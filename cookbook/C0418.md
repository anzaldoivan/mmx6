# Bisect a red grouped R5 instead of isolating the whole group

- Trap (3.0 T4): grouped propagate (`--keys-from`) ran one program_r5 over every unit's gated members. One red R5 re-ran all units isolated. In 1.8.1 that isolated 944 of 952 SLUS units and took 71184 s (.run/logs/health4.log:25179).
- The red cause was `group R5 body sha1 changed since R1 (<another key's shared body>)`.
- Mechanism: R3 `declsync.sync` rewrites prototypes in every file the program includes (declsync.unit_files). That includes other keys' shared bodies.
- bank.ladder's R3 guard only protects the key's own body. So program_r5 sees another key's body sha1 move. An isolated run never sees it, because the edited body belongs to no checked unit.
- Move: on a red group R5, restore and split the units in halves, in key order. Re-gate each half and run its R5.
- A green half keeps its grouped verdicts. A red half recurses, and a red single unit runs isolated. The cost is about 2 R5 runs per level.
- Result on a 30-key SLUS subset: 1598 s before, 349 s after, identical verdicts. The control without the clashing key took 146 s. th-equiv stayed identical.
- GROUP line: `... fallback yes|no reisolated <r> r5 <k> wall <s>s`. Here reisolated counts units re-run isolated after the plan.
- Picking a reproducing pair: both keys must gate alone. A body inside a unit file fails R1, and then the fallback comes from refusals, not from R5.
- Harness: `mx.sh run` passes no stdin. Put the `--keys-from - < list` file under /work/.run, which sync keeps.
- Harness: sync also wipes extracted/. Run `make extract build th-census th-sig` before propagate.
