# C0251 — Overlays see exe symbols only by func_/D_<addr> name: renaming an exe symbol overlays call breaks their link
tags: rename,overlay,link,provide,symbols,x4 · date: 2026-10-25 · phase/task: 1.10/T8 · origin: mmx6 T8.c1

- Overlay links resolve exe (SLUS_013.95) symbols only by their address spelling. Makefile `build/%.elf` PROVIDEs each undefined `(D|func)_<8 hex>` at the address it spells. Splat's per-overlay `undefined_*_auto` files do the rest. A named exe symbol is not visible to an overlay link.
- So renaming an exe symbol that overlay C calls directly breaks the overlay link. tools/mmx6/rename.py refuses it (`RENAME REFUSE ... exe name used by overlay <f>`). An overlay that reaches the name only through a `#define old X` block around a shared body is safe and gets rewritten.
- To lift the refusal, change the build: give overlay links the exe's named symbols, e.g. a PROVIDE per renames.tsv row. Example refused: SLUS 0x8002D2B0 move_object (369 src files).

Source: phase 1.10 T8 (phase-ends/current/logs/T8.c1.md).

Update (1.10/T9.c1, commit 824e0ace): the limit is lifted.
- The `build/%.elf` rule also PROVIDEs every `nm -u` name that config/symbols.SLUS_013.95.txt defines. The address is the same, so it is byte-neutral.
- rename.py no longer refuses exe names that overlays use. It refuses `<new> defined in overlay <p>` instead.
- An exe rename skips the include-without-`#define` refusal, because the new name links in every overlay.
- 31 x4 renames, move_object among them, built 57 of 57 hash OK.
