# C0460 — Repin hold on conflicting types: give every TU declaration upstream's type
tags: x4,repin,hold,conflicting-types,declaration,unity · date: 2026-11-14 · phase/task: 3.2/T2 · origin: 3.2 T2.c1

- Symptom: x4port --repin holds a file with `conflicting types for 'func_X'`. A sibling unit in the same unity TU forward-declares func_X with an X6 type (e.g. void). The upstream body returns s32.
- Move: give every forward declaration in the TU (all #included siblings) upstream's type. Keep the re-ported body exactly as upstream has it.
- Condition: the call sites already cast the callee, so the call codegen does not change. A later repin then reads the function as "same" and does not bring the conflict back.
- Evidence: 3.2 T2.c1, 8001A9B0.c func_8001B6D0 void to s32 in 8001A9B0.c:11 and cd/str_movie.c:11 (TU 120A0.c). FLEET 57 of 57, no debt move (b54a6e6f).
- Also a parameter type: T2.c2 changed func_80039C40 from void* to struct X4_PlayerObj* in movement.h:23 and 800357A8.c:175 (TU 32208.c). Overlay TUs keep their own void* externs.
- Fresh volume: besides the C0271 chain, the volume has no .run/mmx4. Copy the host clone to waves/<scratch>/mmx4 and `mx.sh push` it. Then copy it to /work/.run/mmx4 in the container (never fetch).
- Build outputs cannot be pulled (firewall), so x4port runs only in the container.
- Exception: when the TU calls the callee with different argument counts (m2c leftovers), no prototype fits. Use the unprototyped form the TU already uses (`M2C_UNK f();`). Upstream's direct calls still compile and the bytes hold (T2.c3, clear_object_slot in TU 4228C.c, d2d791b8).
- See C0216 (gate R2 conflicting types), C0257, C0271.
