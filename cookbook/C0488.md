# C0488 — Bank repair-lane gated rows through live propagate.py with the key, not bank.py with the row
tags: bank,propagate,unitcut,relocdef,repair,registry,twin · date: 2026-11-16 · phase/task: 3.3/T4 · origin: mmx6 3.3 T4.c1

When: you bank a row that `refusecause.py --repair relocdef --repair unitcut` gated. This matters most when its gate line says `[via unitcut]`.

- `bank.py <prog:vram> --repair relocdef --repair unitcut` never runs the unitcut cut. The cut lives only in propagate.py (`bank.uc_due`, propagate.py:366 and :397).
- So bank.py feeds a unitcut row the exemplar's whole unit, and the row stops at R2. In 3.3 T4.c1, rock_02 0x800F5170 got all of src/SLUS_013.95/8004FF7C.c and three unrelated symbols conflicted.
- `bank.py <row> --src <exemplar body> --define old=new` banks a relocdef-only row at R5. But it writes no registry row. The member stays `refused` in config/dedup_registry.txt, so the registry and ledger checks disagree after it.
- Bank a draft (a new exemplar) with `bank.py <row> --src src/shared/<prog>/func_<vram>.c`. This writes a `gated exemplar` row.
- Bank gated members with the live `propagate.py <key> --repair relocdef --repair unitcut`, one key per step. Run it first with `--dry-run` to see which members gate.
- The live run retries every refused member of the key. Count the members that gate against the cap of 35 banks per wave first.
- Source: 3.1 W302 banked its repair rows through propagate.py (R3.1-011 b). The playbook rows 1a and 7 say "bank with bank.py --repair". Read that as this route.
