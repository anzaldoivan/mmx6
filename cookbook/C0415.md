# A jtbl carve refused `non-contiguous` by a gap of same-TU tables: carve.py jtbl now bridges it
- Check first: list the dlabels in the gap (`asm/<prog>/data/<gap>.rodata.s`) and grep which nonmatchings/<tu>/ .s references each. If all of them are dispatchers in the same TU, the gap is the unit's own rodata, not a second range.
- One .o has one `.rodata` input section, so a TU cannot really hold two separate ranges. Carving the gap is the only way that moves no bytes.
- `carve.py jtbl <prog> <target lo>` (2.7 T11.c1) carves every gap table too. A table followed by zero pad (below the alignment) is written as `rodata <lo> <hi+pad> <tu>`. A jtbl row's hi comes from boundaries.txt and cannot hold pad. A table with no pad stays a `jtbl` row. A foreign-TU table, data or other byte in the gap still refuses `non-contiguous`.
- Afterwards remove the split stamp and the unit's .c.o, re-split, `make build`, `corpus.py --all` (C0396).
- mmx6 2.7 T11.c1 (457c373a): 12 tables of func_8002E974/8002EE10/8002F06C plus jtbl 0x80010C70 (func_8002F9DC) into 21BF4. `.rodata 21BF4` = 0x800100B4-0x80010D70.
- Bank risk: the 4-byte pad after each table has to come from gcc's 8-alignment of switch tables (C0226/C0296).
