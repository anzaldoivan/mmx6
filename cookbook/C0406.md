# C0406 — Pair a PSX function with its x86 port twin: const-table search, then call graph
tags: pc-port,x86,ghidra,pairing,prior-art,shape · date: 2026-11-07 · phase/task: 2.6/T33 · origin: mmx6 T33.c1

Problem: pair a PSX function with its twin in a symbol-less x86 port (MSVC 7.0, same C) when most of its data is bss.
Move:
- Import the PC exe into its own Ghidra project outside the repo (default PE loader, full analysis, ~35 s).
- Table search first: the bytes of a pointer-free const table the function reads occur once in PC `.data`. Its sole
  referrer is the twin (func_800144DC -> 0x42F560 via D_8006E1D4).
- bss-only functions: pair one callee or caller first, then walk the call graph. Callers with the same call count
  and call order confirm it (func_80013DE8 twin calls wait_for_file_load's twin 4 times, as on PSX).
- Immediates can fail: the port dropped the CD timeout path (0x259 has 0 hits).
- The port is unoptimised (/Od): globals reload per statement, loops are top-tested. Statement order and access widths
  read straight off the listing. The PC call boundaries show where PSX code inlined a callee.

- Result (2.7 T1): all three PSX twins matched pin-free from these shapes. Check each shape against
  the target asm first. PC-only code (an extra test or branch) and dropped paths (a timeout) do occur.
- Pairing (2.7 T9.c1): 7 of 7 paired, high, in ~12 min. bss-only callers pair by call-order signature: the one
  x86 function whose callee sequence (e.g. AAABABCC, or 21 calls with 13 to one callee) matches the PSX caller's.
  Then its callee at the same position is the twin. Neighbouring functions pair 1:1 in address order.

Trap: only facts go into git (G12), and decompiled text stays in ignored `.run/`. PC prim headers are 1 byte longer.
