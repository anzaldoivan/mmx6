# C0458 — A cross-project twin table is stale: re-read state from both trees, keep only its keys
tags: twins,x5,leads,stale,port · date: 2026-11-13 · phase/task: 3.1/T24 · origin: T24 lane join

Symptom: a cross-project lead table says a function is asm, or lists no donor, but the table is weeks old. The tables are mmx5 `docs/oracle/x6-twins.tsv` and `x6-leads.tsv`, and our `campaign/x4/x5-twins.tsv`. At 3.1 T24, 1554 of its 1623 X5 asm rows were C. 24 of the 31 usable X6 donors were not listed as C.

Move: keep the table's twin classes (the key column), and read the state again from both trees. X5 is C when a tracked `src/slus/func_<VRAM>.c` or `src/rockx5/func_<VRAM>_ovlNN.c` has no `INCLUDE_ASM` (C0426). X6 is C when no `INCLUDE_ASM("asm/<prog>/...", <name>)` names it and a definition exists under `src/<prog>/` or `src/shared/`. Follow renames by (prog, vram) through `config/x4/renames.tsv`, since the table holds old names. A function name alone is not unique across overlays: match on the program too.

Traps: a definition regex misses multi-line signatures, so grep the unresolved names by hand. A twin member may have no definition of its own: look for `#define <exemplar> <member>` before the shared include. `build/corpus/functions.jsonl` is in the container, not on the host, so the generator (`imgtab.py x6`) cannot run from the host tree alone.

Check: the state cross-count has no row that went from C to asm on our side, and each donor path opens.
