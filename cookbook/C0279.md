# Fix a workbook address to an overlay member by its instruction word

When: a community sheet cites code by RAM address and instruction word (Tweaks BossHealth.tsv, `ROCK_X6.BIN` blocks).
Many overlay members load at one base: 0x800E9860 for members 2-32, 0x800FA000 for 33-58.
So the address alone names no member and no stage.

Move: for each cited (vram, word), scan every `extracted/retail/rock/NN.bin` whose load range holds the vram.
Take the base from config/loadmap.txt.
Keep the members whose 4 bytes at `vram - base` equal the cited word (little-endian).
One hit fixes the member. Join it to the objects.tsv rows of that member for stage evidence.

Result (2.3/T9): 41 BossHealth entries gave 38 single-member hits, 2 double hits and 1 exe address.
Every boss id matched its stage's member: Yammark rock_03 and rock_33 (boss rush), Gate rock_24.
It also resolved an `ambiguous-prog` ovl_800FA000 row (0x800FE988 is in rock_33).
For a double hit, use the stage join.

Also: the stage index is PlaythroughTable.tsv 0x800CCEDC (high byte stage, low byte sub).
Our `stN.s` ids are decimal: the redux capture logs the title screen as 14 (0x0E).
The script is about 30 stdlib lines in scratch (T9 log).
Byte evidence fixes the member and the stage, not the object link.
Objects still need at least 3 runtime frames.
