# C0468 — Bank R4 +4 after a jtbl carve: retail table at 4 mod 8, the carved unit frame is off by 4
tags: bank,r4,jtbl,carve,rodata,alignment,unit-frame · date: 2026-11-14 · phase/task: 3.2/T5 · origin: mmx6 3.2 T5.c1 W306

When: a jump-table function matches standalone after `carve.py jtbl` put its table in its unit.
The bank then stops `R4: rodata needs placement (+4 bytes)`. The retail table address is 4 mod 8 (check `jtbl_<addr>`).

Cause: cc1 emits the compiled jump table 8-aligned inside the unit's .rodata. The carved unit's .rodata starts 0 mod 8.
So the table lands 4 bytes later than retail. The retail tables sit 8-aligned from a 4-mod-8 origin.
The original object's .rodata did not start where our unit does. bank.py's R4 is right: placing the body by hand reddens the hash.

Check: in the container, replace the INCLUDE_ASM by an #include of the draft and `make -B` the unit object.
Read its .rodata size with `objdump -h` (3.2 T5.c1, 4228C: 0x84 -> 0x88). Link, compare the binary sha, restore.

Not a fix: draft changes, `--repair` switches, or the C0415 bridge (its pad rows are this same alignment).
Next lever, untried: move the unit's rodata or TU boundary so the object's .rodata origin is 4 mod 8 (opt cut, C0288).

Evidence: 3.2 T5.c1, W306: func_800315CC, func_800319EC (30234), func_8003AAD0 (32208), func_8004E26C (4228C).
T4 saw the same +4 for func_8001A3D4 (120A0, jtbl 0x80010068). func_80030D80's table at 0x80010F38 (0 mod 8) banked.
Solved: the opt cut works for all four frames (3.2 T12.c1, C0483).
