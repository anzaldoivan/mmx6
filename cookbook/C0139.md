# C0139 — Load/store order across bases: dead-store deletion, char aliasing, symbol bases decide what the scheduler moves
tags: lever,dead-store,flow,alias,char,sched,store-order · date: 2026-10-04 · phase/task: 1.8.1/T5 · origin: mmx6 W5

These memory-op ordering facts come from gcc 2.95 PSX drafts:
- flow deletes an earlier same-address store when a later store overwrites it with no intervening aliasing read. If retail keeps both, put a char-typed global read (assigned to a local) between them (c45).
- In retail, a store sunk below a global load hints that the source statement that reads that global came first. The scheduler cannot move a pointer-param store above a possibly-aliasing global load (c45).
- Loads do not rise above char (u8/s8) stores through `self` (char aliases everything) (c4 c18 c21 c26 c61). When both have a known symbol base, sched1 hoists a load above stores (c67).

Use: these facts apply to load/store order residuals across different bases. Before anything heavier, change source statement order, the access type (char vs wider) or the base spelling (symbol vs pointer).
