# The first statement after a do-while(0) loop-end note is a scheduling barrier: choose it

Symptom: after a do { ... } while (0) block, a reload and a store schedule in the wrong order. The reload should go first.

Cause: the insn right after the loop-end note acts as a barrier. Whatever statement lands there pins its position and everything after schedules freely.

Lever: end the do-block by reading the value into an s32 local. Then make the store the first statement after the loop. The store is then the barrier, and the parent reload and state read schedule after it as in retail.

Evidence: W15 rock_24 F4790 (retry). The first attempt failed on this order.
Related: C0136 (do-while(0) as a barrier for a delay slot), C0162 (do-while(0) for a callee-saved swap).
