# Repin to a new mmx4 pin: refetch the clone by hand, and expect homed member names to hold most files

When: `x4port --repin` at a new `config/refs.toml` mmx4 ref (2.6 T31: 807a01b -> 4e16dfc).

- x4core never refetches an existing clone. It prints `.run/mmx4 at <old>, pinned <new> (remove .run/mmx4 to fetch the pin)`.
  `rm -rf .run/mmx4` in the container, then `x4share.py --triple gcc2.95.2-psx-aspsx2.86 --partners` fetches it. x4core has no ensure_clone CLI.
- The repin unit is one adapted function, not one file (2.6 T31: 98 same + 61 changed = 159). Several live in one role file (80049670.c: 12).
- The main hold cause was homed structs. Upstream bodies use `unk5`, `unk6`, `unk15`, `unk28` or `unk2`.
  Our homed X4 struct (player.h `X4_PlayerObj`) carries X6 role names there (`action`, `action_phase`). That held 54 of 74 units in 35 files.
- Hash breakers among compiling bodies: dump `.text/.data/.rodata` of each TU object with the new bodies.
  Swap the old bodies in, rebuild and `cmp`, in one run with no `make expected`. Then try each candidate alone. 3 ladder/ files: C0258 dropped casts.
- `mx.sh pull include` also pulls a regenerated include/macro.inc: pull single files.
- x4port does not validate the hold.tsv pin column. A file may sit at an older short pin (80039C40.c `@29b62af`).
