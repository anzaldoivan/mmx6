## Rationale
- Order: pins (T1) → exe pipeline proven with coarse segments (T2) → segmentation rules (T3, parallel with T2) → segments at forced boundaries + boundary check (T4) → 56 overlays (T5) → fleet, expected, contracts promoted, docs (T6). The exe first isolates the pipeline on one binary (M6) before fanning out to 56; segmentation lands before any overlay yaml is written so overlays are generated once, already segmented (DK-12).
- T1 separate: a toolchain change rebuilds the image and needs its own clean evidence; `make toolchain-check` asserts the pins at every build (M10), so a drifted image fails loudly instead of silently mis-assembling.
- T3 is `review: yes`, `coder: none`: the constitution (PROJECT_CONTEXT.md:536) routes the segmentation decision to `/discuss max` or splitting until routine. The plan splits it: T3 writes concrete, mechanical rules from config/boundaries.txt (each lib span its own subsegment, each jtbl table in its function's TU, fstart = symbol not TU, VM_VIB never a split point, ambiguous_name/overlapping spans resolved by a stated tie-break) with counts per binary; the developer reviews and may open `/discuss max` on it before T4 consumes it. Preset has no hard rung, so no task is `effort: high`; all six are medium.
- T4 generates the yamls' subsegment lists with a one-shot generator (`tools/mmx6/segment.py`) instead of hand-writing ~800 boundaries: 57 configs justify a tool (C0003); afterwards the yamls are hand-edited (asm → c in later phases) and the permanent guard is the boundary check, not the generator.
- T5 one task for 56 overlays: same config shape, only vram/size/jtbl differ; per-binary Makefile rules come from a pattern over a binary list, not 56 hand rules. Fan-out by agents not needed: a generator + one build loop.
- Contracts: one `config/check.<bin>.sha` per binary (57 files) so a failure names its binary and the firewall glob covers them. The audit treats `required:` hashes as forbidden for tracked files; the check files contain hashes, their own sha1 differs, so they pass (verified in T6 by the audit itself). Whether `required:` accepts a glob is read from config/firewall.txt docs (:7-8, :40); if not, 57 explicit lines.
- `make expected` = copy of the green `build/` outputs into ignored `expected/` (the differ baseline for 1.4); set from a clean build, never from extracted files directly, so it proves the build reproduces them.
- No `## Developer decides` items: tooling, segmentation mechanics and ordering are engineering; the segmentation sign-off happens at T3's review.

## Risks
- splat's psx output may not reassemble byte-identically (macro expansion of `li`/`la`, branch delay reordering without `.set noreorder`, `%gp_rel` vs gp_value, section alignment padding, jtbl alignment after rodata migration): T2 isolates on the exe first; a resisting construct goes to `bin` subsegment only with a logged reason, never silently.
- splat64 pin: newest version confirmed by the web report is 0.50.0 (2024-11); a newer one may change config keys. T1 checks live and pins what installs.
- Overlays share bases: a symbol file or linker script shared across binaries would collide; one yaml/ld/symbols per binary is the rule.
- Overlay sizes not ≡ 0 mod 4 and data tails inside overlays (jump tables, strings) may mis-disassemble as code; `sha1sum -c` catches it, the fix is a `data`/`bin` subsegment at the evidence.
- Segmentation rules may prove wrong only when C arrives (1.4+); DK-12 says the cost grows with matched work, hence T3's review before T4.
- Fleet runtime: 57 splits + links may exceed 285 s; every fleet run goes through `run.sh --bg/--wait`; if > 10 min, `-j` and splat caching are T6's to fix (C0004).
- `sync` wipes extracted/: a forgotten `make extract` reads as a missing-file failure, not a hash failure.
- Firewall: a tracked file equal in sha1 to a game binary fails the audit; nothing generated (asm/, build/, expected/) may leave the container or enter git.
