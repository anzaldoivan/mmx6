# C0497 — A key with two exemplar rows: unitcut rewrites the shared path of both rows, and th-harness P2 fails
tags: repair,unitcut,registry,exemplar,harness,P2 · date: 2026-11-19 · phase/task: 3.3/T8 · origin: mmx6 3.3 T8.c2

Symptom: in 3.3 T8 (W311) the bank gated and the whole-binary hashes stayed green.
But `make fleet` printed FLEET 57 of 57 with rc 2.
th-harness failed with `HARNESS CONTROL FAIL P2 compiles? gather raised SystemExit`.
Running harness.p2_gather on its own gave `probe: func_800F4B50 not defined in ...src_shared_rock_09/func_800F4A90.c.o`.

Cause: key e98ec56a has two exemplar rows in rock_09, at 0x800F4A90 and at 0x800F4B50, with identical bodies in one unit.
The live run moved the first body into a new shared file.
Then it rewrote the shared path column of every row of the key.
That included the second exemplar row, whose body still lives in its unit file.
The propagate tool is frozen, so this is a data fix now and a tool fix later.

Move: after a live key run, check each `gated exemplar` row whose path is under src/shared. The file must define that row's function, or its name from config/symbols.<prog>.txt.
For a row that fails, set the shared path column back to the HEAD value, the unit that still holds the body.
Then sync and run the fleet again.
A key with two or more exemplar rows is the case to watch. The tool fix is for unitcut's registry rewrite to touch only the cut exemplar's rows and its members.

Evidence: config/dedup_registry.txt:727 (HEAD 3a2bf71a against the W311 bank), .run/3.3/t8/c2/fleet.log:13234, .run/3.3/logs/t8c2-p2dbg.log.
