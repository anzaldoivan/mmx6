# Unifying a callee's prototype can redden the hash even when no caller reads the result
- Extends C0361. Retyping sibling prototypes (`M2C_UNK` <-> `void`) changes gcc 2.95 CALLER codegen.
  The register choice (v1/v0) and branch targets move, although no caller reads the result.
- Case T20 func_800139F4: 38 int and 12 void prototypes. Either unification turned the SLUS hash red (unit 32208).
- Fix: one program-wide prototype `s32 f(s32);`, the banked `M2C_UNK (M2C_UNK)`.
  Each call site that needs the void form calls through a cast: `((void (*)(s32))f)(x);` (8001C718.c:1053).
- Check: a whole-binary hash after every prototype edit, before the gate.
- Trap: gate tusync respells same-program prototypes as `M2C_UNK f(M2C_UNK a0);`, also in files with no
  `#define M2C_UNK`. The fleet build passes. Harness P2 standalone compile fails (parse error). Spell those `s32`.
