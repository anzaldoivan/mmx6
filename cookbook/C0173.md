# Block order of a range test: inverted test jumping to the shared block, then goto the call

Symptom: m2c's nested if/else places a shared arm (a state store, a shared call) after the other tests; retail tests the first range bound and jumps straight to the shared block, falling into an unconditional jump to the call.
Cause: gcc emits blocks in source order; the nesting decides which arm falls through.
Lever: write the first arm as the inverted test, `if (!(cond)) goto shared; goto call;`, with the shared block's label placed where retail puts it (inside the then-arm of the earlier test if needed) and later cases jumping back to it with goto.
Evidence: W16 SLUS 4CD3C (case 1 range tests), rock_02 EDBB4 (shared func_80049E50 arm as the then-arm with its label inside, 32/46 to match).
Related: C0144 (nested ifs with a goto to a shared label), C0157 (case bodies in block order).
